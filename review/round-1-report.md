# 第一轮评审：计算逻辑边界测试（画像1—3）

评审日期：2026-08-18  
评审分支：`review-round-1-calc-boundary`  
评审方式：只读代码审查 + 按当前 JavaScript 逻辑复算。未修改计算公式、合规文案或生产代码，未部署。

## 🚨发现潜在合规风险

### 1. “测算年度/用工年度/申报年度”没有清晰分开

页面把 `targetYear` 同时展示为“计划用工年度”和报告“测算年度”，但残保金申报使用上年度在职职工人数、工资总额及残疾人就业人数。2026年联网认证核验的是2025年度就业情况；2026年新招聘通常影响后续年度认定，不能用于倒推减少已经形成的2025年度应缴额。当前页面把“现在应缴”和“2026年招聘后应缴”放在同一组老板结论中，容易让临近申报的企业误解为当年临时招聘可冲减当前申报。

建议：把“就业发生年度”“联网认证/申报年度”拆为两个明确字段，并在结论中写清“本年度真实就业影响下一年度申报”。此项涉及申报口径，**⚠️需人工审核**。

### 2. 当前日期已过默认入职月份，仍按全年计入

截至评审日2026-08-18，页面默认 `targetYear=2026`、`startMonth=1`。`calculate()` 仅计算 `months = 13 - startMonth`，不校验月份是否已经过去，因此默认结果把尚未发生的2026年1—8月当作已真实在岗。该行为与页面现有“不倒填月份、不补造考勤/工资/社保记录”提示直接冲突。

建议：过去月份不得作为“计划入职月份”直接计算；若填写过去月份，必须要求确认这是已经真实发生且可核验的历史用工，否则停止给出金额。**不得删除、简化或弱化现有合规提示。**

### 3. 31人边界的差额人数未按广东指南显示的两位小数口径参与计算

代码用未舍入的 `31 × 1.5% = 0.465` 直接计算金额，但广东税务既有指南写明差额人数可保留小数点后2位并四舍五入。页面虽然显示0.47人，金额仍按0.465计算，形成“展示代入值”和“实际内部乘数”不一致。

若按0.47计算，本例应缴额为 `0.47 × 36,292 × 90% = 15,350.72元`；现代码输出15,188.20元，相差162.52元。

**⚠️需人工审核：**是否必须在乘法前四舍五入，应以广东电子税务局当期计算结果或主管部门书面口径复核。任何公式改动均不得直接采纳。

> 该改动如被人工确认，基于以下信息来源：[广东省残疾人就业保障金政策指南（广东税务官方PDF）](https://guangdong.chinatax.gov.cn/webapps1/gdsw/gzsw_zcjd/201808/ab59919923914004a1b866553c78ed5b/files/8b550d4ddd954cefa67c2c8be6804476.pdf)，其中载明差额人数可保留小数点后2位（四舍五入）。在未与当前电子税务局口径核对前，本建议仅为草稿，不得直接采纳。

### 4. 即将离职的现有残疾职工没有动态输入，可能低估应缴额和补员人数

页面只有“现有已认定残疾职工年平均人数”，没有离职月份、预计剩余在岗月份或“已发生/预测”区分。若HR把“当前仍有1人”直接填成1，系统输出9,073.00元且建议新增1人；若该员工离职且全年平均认定数回落为0，则同一企业输出48,994.20元且建议新增2人。系统没有主动提醒这一敏感性。

## 1. 计算逻辑文件与位置

当前项目为单文件前端，计算和参数均在：

- `index.html:1091`：`CITY_POLICY` 城市最低工资、计征工资上限和核验年度。
- `index.html:1184`：`applyCityPolicy()` 年度与地区参数匹配。
- `index.html:1329`：`getTier()`，达到1.5%为0、1%—1.5%为50%、低于1%为90%。
- `index.html:1413`：`calculate()` 主计算函数。
- `index.html:1434`：30人（含）以下免征判断 `staff <= 30`。
- `index.html:1439`—`index.html:1441`：基准差额人数与基准应缴额。
- `index.html:1443`—`index.html:1471`：招聘人数、按月折算、各方案应缴额、成本与净收益。
- `index.html:1870`以后：老板结论、公式代入、方案对比和风险提示渲染。

公式本身未改动：

`应缴残保金 = max(0, 上年平均人数 × 1.5% − 已认定残疾职工年平均人数) × min(企业年平均工资, 当地工资上限) × 分档征收系数`

## 2. 共用测试假设

为能完整运行现有代码，三个画像统一采用以下测试值：

| 参数 | 测试值 | 说明 |
|---|---:|---|
| 城市 | 广州其他区 | 仅用于复现代码路径 |
| 目标年度 | 2026 | 页面默认值 |
| 计征工资上限 | 36,292元/年 | 代码中的2021年历史参考值；**不代表2026现行值** |
| 规定比例 | 1.5% | 只读系统参数 |
| 入职月份 | 1月 | 用于复现全年12个月逻辑 |
| 人数认定系数 | 1 | 普通残疾职工 |
| 月工资 | 2,500元 | 广州代码默认值 |
| 企业社保公积金 | 1,900元/月 | 页面默认估算值 |
| 其他成本/一次性成本 | 0 | 控制变量 |
| 所得税节省 | 不纳入 | 页面默认关闭 |
| 固定费/成功分成 | 0 / 20% | 净增益为负时成功分成为0 |

由于广州上限仅核验至2021年，以下金额只能用于测试程序行为，不能作为2026申报结论。

## 3. 画像1：29人企业主

### 输入

- 上年平均在职人数：29人
- 上年度工资总额：1,740,000元（年平均工资60,000元）
- 现有残疾职工年平均人数：0人

### 当前代码输出

| 项目 | 输出 |
|---|---:|
| 原始差额人数 | 0.435人（界面显示0.44） |
| 分档 | 90%档 |
| 是否小企业免征 | 是（29 ≤ 30） |
| 现在预计应缴 | 0.00元 |
| “满额安置”新增人数 | 0人 |
| 合作后应缴 | 0.00元 |
| 用工成本/净收益 | 0.00元 / 0.00元 |

### 体验与诚实度评价

- 优点：老板结论会明确提示“30人及以下企业，预计无需缴残保金”，不会诱导为了残保金而新增招聘。
- 遗漏：系统只读取上年平均人数，不询问下一年度是否会因正常扩招跨过30人线，也没有“30人必须来自真实、完整的月平均用工数据”的醒目提醒。
- 当前没有“临界操作本身有稽核风险”的专门提示。更准确的表达应是：不得通过漏报、拆分、倒填或虚构人数制造30人以下条件；正常经营导致的人数变化本身不能武断描述为违法。该文案涉及法律定性，**⚠️需人工审核**。

## 4. 画像2：31人企业主

### 输入

- 上年平均在职人数：31人
- 上年度工资总额：1,860,000元（年平均工资60,000元）
- 现有残疾职工年平均人数：0人

### 当前代码输出

| 项目 | 输出 |
|---|---:|
| 原始差额人数 | 0.465人（界面显示0.47） |
| 适用计征基数 | 36,292元（历史参考） |
| 分档 | 90%档 |
| 现在预计应缴 | 15,188.20元 |
| 满额方案 | 新增1人，全年在岗 |
| 招聘后年平均人数/残疾人数 | 32人 / 1人 |
| 招聘后比例 | 3.125% |
| 合作后应缴 | 0.00元 |
| 残保金节省 | 15,188.20元 |
| 新增用工成本 | 52,800.00元 |
| 扣成本后净收益 | -37,611.80元 |

### 体验与诚实度评价

- 优点：结论能明确指出“虽然可以免征，但扣除工资社保后是净成本”，没有把免征包装成盈利。
- 问题：差额人数显示0.47但金额按0.465计算，用户用页面可见公式无法复算出同一金额。
- 问题：36,292元是历史参考参数，尽管页面有“待核验”提示，老板主卡仍直接显示精确金额，容易形成过度确定感。

- 上年平均在职人数：100人
- 上年度工资总额：6,000,000元（年平均工资60,000元）
- 现有残疾职工年平均人数：1人

| 残保金节省 | 9,073.00元 |
| 用工成本 | 52,800.00元 |
| 最终净收益 | -43,727.00元 |

### 输入B：离职后按全年认定0人测试

| 项目 | 当前代码输出 |
|---|---:|
| 当前安置比例 | 0% |
| 分档 | 90%档 |
| 差额人数 | 1.50人 |

### 体验与诚实度评价

- 建议把“现有已认定残疾职工年平均人数”拆为：已发生月份、预计离职月份、预计可计入年平均人数，并同时展示“留任/离职”两种结果。实现前必须说明当前无此功能。

## 6. 本轮问题清单与改动建议

| 优先级 | 问题 | 建议 | 是否涉及公式/敏感文案 |
|---|---|---|---|
| P0 | 申报年度与就业年度混用 | 双年度显示，明确次年申报影响 | ⚠️需人工审核 |
