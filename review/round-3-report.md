# 第三轮评审：产品设计与诚实度测试（画像7—9）

评审日期：2026-08-18  
评审分支：`review-round-3-product-trust`  
评审方式：只读代码、数据库结构和静态文案审查 + 按当前逻辑复算。未修改生产代码、合规文案或计算公式，未部署。

## 🚨发现潜在合规风险

### 1. 临近申报用户可能误以为“现在招聘”能减少当前申报期残保金

广东2026年联网认证核验的是2025年度就业情况，残保金申报也使用上年人数、工资和已安置人数。当前页面将“现在要交多少”“计划在2026年入职”“合作后还要交多少”放在同一个即时结论里，没有明确说明2026年真实就业通常影响后续年度申报，无法改变已经结束的2025就业事实。

对画像9，这是可能导致经营决策误判的核心风险。建议在任何招聘方案前固定展示：

> 当前申报期对应的是上年度已经发生的真实就业数据；本年度新招聘不能倒填或冲减上年度数据，只能按实际在岗月份影响后续年度认定。

此提示只能新增和强化，**不得删除、简化或弱化现有“不倒填月份、不补造考勤/工资/社保记录”文案。**

### 2. 页面允许选择已经过去的月份作为“计划入职月份”

评审日为2026-08-18，但默认目标年度2026、入职月份1月，系统仍按12个月计算。代码没有当前日期检查，也没有要求证明该月份已经真实发生。用户若把过去月份当“计划”填写，结果只能通过倒填月份才可能实现。

建议：过去月份仅在用户明确选择“已真实入职”并确认已有合同、工资、社保、考勤记录后才允许作为历史数据；未来计划不得回填过去月份。该改动涉及合规流程，**⚠️需人工审核**。

### 3. 挂靠风险说明缺少任务要求的完整三段信息

当前文案明确拒绝“挂证不上岗”、倒填和补造，方向正确；但没有完整说明：虚假就业/虚假申报/重复就业的识别，联网认证与监督管理部门的数据核验机制，以及提交虚假资料可能承担的法律后果。代码也没有针对“找关系”“不用真的招人”等追问的专门拒绝逻辑。

“挂靠是否统一定性为骗保”属于法律表述问题，本评审不自行下结论。若需使用“骗保”一词或列出追缴、处罚、刑事责任等具体后果，必须由律师/税务专业人员确认。**⚠️需人工审核**，不得用新文案替换或弱化现有风险提示，只能在其后补充完整说明。

## 1. 画像7：中介/代理一次给5—10个客户批量测算

### 当前实际具备的能力

1. 单个企业内可比较“保持现状、招聘1—4人及满额附近方案”。这是同一企业的招聘方案比较，不是多企业比较。
2. 腾讯云正式站点可在用户主动同意后保存一条测算记录，表结构见 `cloudbase-postgresql.sql`。
3. 数据库RLS只允许匿名/登录用户读取自己的记录；`service_role` 才能读取管理数据。
4. 页面存在“后台管理”UI，可配置外部API地址、筛选和导出CSV。

### 当前没有的能力

- 当前没有批量导入5—10家企业的功能。
- 当前没有多企业横向对比表。
- 当前没有“复制客户方案/再次测算/版本对比”功能。
- 当前没有已经部署并配置好的后台查询API；管理员必须手动填写接口地址和Bearer Token。
- 当前不能仅凭前端后台页读取全部客户记录。匿名RLS只允许读取各自记录。
- CSV导出依赖先从后台API加载数据；API未配置时该功能不能导出数据库记录。

因此，不能对用户宣称“批量客户管理已实现”。准确状态是：**单次保存的数据结构和后台列表前端已准备，但批量工作流与安全后台接口当前无完整可用功能。**

### 产品建议（不在本轮假装实现）

| 优先级 | 建议 | 诚实度要求 |
|---|---|---|
| P1 | 客户工作台：企业列表、最后测算时间、政策状态、净收益 | 后台API未上线前显示“建设中”，不能展示空壳成功状态 |
| P1 | CSV模板批量导入，逐行校验缺失政策参数 | 缺失值保持“待核验”，不得补0 |
| P1 | 多企业对比：应缴、节省、成本、净收益、参数年份 | 历史参数与现行参数必须分组 |
| P2 | 同一企业多个版本及变更原因 | 保留旧记录，不静默覆盖 |
| P2 | 导出前脱敏联系人 | 明确个人信息使用目的与权限 |

## 2. 画像8：反复追问“能不能挂靠/找关系”的用户

### 当前全部相关文案位置

| 文件位置 | 当前内容/作用 |
|---|---|
| `README.md:49` | 只支持真实就业，不支持挂证不上岗、倒填月份或补造考勤/工资/社保记录 |
| `index.html:1077` | 页面底部固定提示“不倒填、不补造” |
| `index.html:1409` | 复制完整方案时的风险说明，拒绝挂证不上岗、倒填和补造 |
| `index.html:1999` | 可打印报告的风险段落，要求真实岗位、劳动、产出、银行发薪和按月足额社保 |
| `index.html:795`附近 | 合规开关：劳动合同、实际到岗、社保、银行发薪且不低于最低工资 |

### 当前拒绝逻辑

当前是纯前端静态测算页面，没有聊天输入框，也没有关键词识别、问答分流或动态拒绝处理。因此：

- 对“挂靠”没有专门交互逻辑；
- 对“找关系”没有任何关键词或兜底逻辑；
- 对“不用真的招人”没有专门问答逻辑；
- 当前只能依靠底部提示和导出报告中的静态风险段落。

必须如实表述为：**当前无此交互拒绝逻辑。**

### 建议的安全处理结构

以下只是信息架构建议，不是已实现功能：

1. 第一次触发敏感意图：明确拒绝挂证不上岗、虚假就业、虚假申报和重复就业；引导到真实岗位方案。
2. 第二次追问“找关系/不查”：说明联网认证会核验合同、工资、社保、残疾证有效性等数据，并要求申报资料真实。
3. 第三次继续要求规避：停止给出降费方案或操作步骤，只提供合法招聘、岗位设计、材料清单和主管部门咨询渠道。

建议补充的完整风险段落必须单独走法律审核，不能混入普通文案改动：

> **⚠️需人工审核：**挂证不上岗、虚假就业、虚假申报、重复就业、倒填月份或补造合同、考勤、工资、社保记录不得作为残疾人就业认定依据。联网认证会结合劳动合同、工资发放、社保缴费、残疾证有效性及重复安置等信息审核，申报单位应对材料真实性、准确性和完整性负责。隐瞒或提交虚假材料的具体追缴、行政或刑事后果，应以主管机关处理及律师审核意见为准。是否使用“骗保”表述须另行法律定性，不得擅自承诺“有关系即可通过”。

该建议不得替换现有“不倒填、不补造”提示，只能在人工审核后补充。

## 3. 画像9：临近申报截止日、时间紧迫的企业主

### 场景A：用户不修改默认值

评审日2026-08-18，页面默认目标年度2026、1月入职。测试输入：广州其他区、100人、年平均工资60,000元、现有残疾职工0人、历史参考上限36,292元。

当前代码按全年12个月输出：新增2人、合作后应缴0元、残保金节省48,994.20元、用工成本105,600元、净收益-56,605.80元。

问题：如果这2人并未在2026年1月真实入职，该结果不可实现；页面没有阻止或醒目警告。

### 场景B：用户如实选择12月入职

| 项目 | 当前代码输出 |
|---|---:|
| 当年在岗月份 | 1个月 |
| 满额所需新增人数 | 19人 |
| 招聘后年平均人数 | 101.5833人 |
| 折算残疾人数 | 1.5833人 |
| 安置比例 | 1.5587% |
| 残保金节省 | 48,994.20元 |
| 1个月用工成本 | 83,600.00元 |
| 最终净收益 | -34,605.80元 |

代码并没有输出“偏低的建议人数”，反而因仅剩1个月将满额人数提高到19人；但是只显示“预计在岗1个月”，没有明确建议顺延到下一就业年度，也没有比较“本年19人×1个月”和“次年2人×12个月”的可执行性。

### 截止日诚实度

- 广东税务办事指南列示残保金申报缴费通常为每年8月1日至11月30日。
- 2026年广东多地联网认证通知核验2025年度安排，时间为3月1日至10月31日。
- 当前页面没有任何地区化截止日配置或倒计时。
- 当前页面不判断“当前申报期对应哪个就业年度”。
- 当前页面不会在超过联网认证时限后停止输出当前申报期可减免的暗示。

### 建议

1. 首页先问“你是测算当前申报，还是规划下一就业年度”。
2. 当前申报只允许输入已经发生的上年度数据，不展示“现在招聘可冲减”方案。
3. 下一年度规划按真实未来月份测算；过去月份禁选，除非标记为已发生并有材料。
4. 剩余月份过少时提供跨年度对比，并明确“建议顺延”是经营建议，不是审批结论。
5. 截止日必须按市、年度、官方通告配置；没有核验就显示“截止日待确认”，不得猜测。
