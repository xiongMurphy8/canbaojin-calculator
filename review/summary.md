# 残保金测算网站三轮结构化评审汇总

评审日期：2026-08-18  
评审范围：3组画像、每组3个场景，共9个画像  
交付状态：三个未合并PR；无生产代码修改；无部署。

## 🚨发现潜在合规风险汇总

### P0：申报年度与真实就业年度混用

网站把“当前应缴”“计划在目标年度入职”“合作后应缴”放在同一即时结论中，但残保金申报及联网认证使用上年度已经发生的数据。2026年招聘通常不能减少基于2025年度数据形成的2026申报金额。临近申报用户可能因此误判。

**⚠️需人工审核：**把产品拆为“当前申报复核”和“下一就业年度规划”，明确本年度真实就业影响后续年度认定。

### P0：过去月份仍可作为未来计划并按全年计算

评审日为2026-08-18，页面默认2026年1月入职，仍按12个月计算；代码不检查月份是否已经过去。这与页面“不倒填月份、不补造考勤/工资/社保记录”提示冲突。

必须保留并强化原合规提示；过去月份只能在确认真实已发生且材料可核验时使用。

### P0：31人边界显示0.47人，内部却按0.465人计算

广东既有官方指南写明差额人数可保留两位小数并四舍五入。31人案例界面显示0.47，金额按0.465计算，用户无法按可见公式复算。现输出15,188.20元；若按0.47计算为15,350.72元。

**⚠️需人工审核：**

> 该改动如被确认，基于以下信息来源：[广东省残疾人就业保障金政策指南（广东税务官方PDF）](https://guangdong.chinatax.gov.cn/webapps1/gdsw/gzsw_zcjd/201808/ab59919923914004a1b866553c78ed5b/files/8b550d4ddd954cefa67c2c8be6804476.pdf)。在未与当前电子税务局口径核对前，该公式改动仅为草稿，不得直接采纳。

### P0：东莞2025参数错误反向覆盖2024年度

代码用 `targetYear <= verifiedThrough` 判断有效，使2025年度36,993元参数在选择2024年时也被标记为“2024年度官方口径已匹配”。需要改为按年度精确匹配。

### P0：最低工资无年度版本

2025-03-01生效的最低工资被用于所有可选年度（2024—2027），会改变历史年度用工成本和净收益。

### P0：即将离职残疾职工可能导致大幅低估

100人案例中，填写现有1人输出应缴9,073元、建议新增1人；若离职后全年认定为0，输出48,994.20元、建议新增2人。当前无离职月份或敏感性提示。

### P0：跨市企业可能被IP自动匹配到错误城市

系统只有“企业所在地”单字段，IP/设备位置可能是HR办公地，不是主管税务机关或联网认证所属行政区。当前无注册地与参保/用工地双地匹配功能。

**⚠️需人工审核：**跨地情形应由主管税务机关和残联确认；系统不能自行编造适用地算法。

### P1：广州历史上限仍生成精确老板结论

广州其他区、增城、从化三个值均为历史口径，代码只核验至2021；目标年度2026时仍可用该数值生成精确金额。应降级为单独敏感性试算，主结论显示待核验。

### P1：挂靠风险说明不完整

现有页面已明确拒绝挂证不上岗、倒填和补造，不能删除、简化或弱化；但缺少虚假就业/虚假申报/重复就业、数据联网稽核及法律后果的完整说明，也没有针对“找关系”的交互拒绝逻辑。

**⚠️需人工审核：**是否使用“骗保”一词及具体追缴、处罚或刑事后果必须先做法律定性；只能在保留原文基础上补充，不能替换原文。

## 三轮结论概览

| 轮次 | 画像 | 核心结论 |
|---|---|---|
| 第一轮 | 29人企业 | 正确输出30人以下免征，但缺少人数真实性和未来跨线提醒 |
| 第一轮 | 31人企业 | 能诚实显示招聘后净成本；差额人数显示与内部精度不一致 |
| 第一轮 | 现有1人即将离职 | 无离职动态，1人/0人结果差异巨大 |
| 第二轮 | 广州增城 | 特殊分区存在，但仅为2021以前历史参考 |
| 第二轮 | 佛山注册、广州用工 | 当前只有单一所在地字段，无双地判断功能 |
| 第二轮 | 低薪劳动密集型 | 正确按企业平均工资与上限取低；最低工资年度版本缺失 |
| 第三轮 | 代理批量测算 | 可逐次保存记录，但无完整批量导入、多企业对比或已部署后台API |
| 第三轮 | 反复询问挂靠/找关系 | 只有静态提示，当前无交互拒绝逻辑 |
| 第三轮 | 临近截止日 | 12月会算出19人×1个月，但不提示顺延；更严重的是过去月份仍可按全年计算 |

## 人工待办清单

### 第一优先级：合规风险

1. 与主管税务机关/残联确认“就业发生年度→联网认证年度→残保金申报年度”的准确映射，并审定双模式产品结构。
2. 立即审定过去月份校验规则；在人工确认前，不应把默认1月全年度结果用于客户正式方案。
3. 在广东电子税务局用31人案例核对差额人数是否应先四舍五入到两位，再决定是否修改公式。未核实前保持草稿。
4. 审定离职员工的按月折算和年平均认定输入方案。
5. 由律师/税务专业人员审核挂靠风险完整段落，尤其是“骗保”定性及具体法律后果；保留全部现有拒绝和“不倒填、不补造”原文。
6. 明确跨市企业以哪个主管行政区参数为准；没有官方确认前只提示人工核验。

### 第二优先级：数据过期与版本管理

7. 建立按城市、区县、年度的参数表，字段至少包括 `effectiveFrom`、`effectiveTo`、`sourceTitle`、`documentNumber`、`sourceUrl`、`checkedOn`。
8. 修复东莞参数反向覆盖2024的问题；所有年度必须精确命中。
9. 为最低工资建立年度版本，禁止2025标准自动用于2024。
10. 核验广州其他区、增城、从化2026计征上限；核验前历史值只做敏感性试算。
11. 补齐其余19市年度计征上限；找不到官方现行来源时保持 `null`，不得猜测。

### 第三优先级：产品体验

12. 后台API未部署前，明确显示“后台接口尚未配置”，不要把列表UI表述为完整后台。
13. 规划客户列表、CSV批量导入、多企业对比和版本管理；实现前明确“当前无此功能”。
14. 增加年末“本年短期方案 vs 次年全年方案”对比及顺延建议。
15. 将企业年平均工资、残保金计征上限、员工最低工资分区解释，避免混淆。
